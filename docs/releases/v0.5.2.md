# v0.5.2

**Two fixes from watching it work on an app that hides its element tree, plus a new hero image.**
Commenting on a WeChat Moments post took **64 steps and 341 seconds**; the same task now takes
**20 steps and 58 seconds**, sent on the first tap. Neither fix is a new capability — they stop the
assistant from wasting turns, and both were found by measuring rather than by reading code.

> **The attached APK is the `debug` build, as a stopgap.** The release build type has no
> `signingConfig` and there is no keystore in this repository, so `assembleRelease` emits
> `app-<abi>-release-unsigned.apk`, which will not install until you sign it. Rather than ship nothing
> while that decision is still open, the attached APK is the debug variant: signed with the standard
> Android debug certificate, and it installs as-is. It is `debuggable`, it is larger than a signed
> release build, and it is **bare** — no keys, English, CodeFlying off. See **[Download](#download)**
> for the two keys you will have to supply yourself before it can do anything.

## Highlights

- **A swipe moves as far as the finger did, and stops there.** It used to lift mid-motion, so the list
  flung several screens past the target and the model lost its place — the single largest cost in the
  64-step measurement. Distance is now the control: to bring something 300 units into view, swipe 300
  units. A new `fling` option keeps the old behaviour for long jumps through a feed.
- **The tap right after typing into a reply box now has to be aimed.** On an app that hides its tree,
  the reply strip is a thin band lying on top of the post below it, so a grid-cell tap aimed at it
  opened that post instead — twice out of two. After blind typing, only a tap that came from a zoom is
  accepted, and the error says so.
- **`submit_input` stops claiming success on a box that cannot be submitted that way.** WeChat's
  comment box only sends from its own button; firing the IME action there answered "done" while
  sending nothing.
- **The tap ring is drawn where the tap landed.** It was sitting a status bar below, on every tap.
- **The README's first image is a phone with the character sitting on it**, instead of a floating head.

## What's Changed

### Fixed

- **A swipe no longer coasts past what the model aimed at.** `swipe_by_coordinates` lifted the finger
  while it was still moving, so the list flung several screens beyond the target. The stroke now
  **holds at its end point before lifting**, and `ACTION_CANCEL` ends a scroll without a fling — so the
  list moves about as far as the finger did, and **the distance becomes the control**. A new `fling`
  parameter (default `false`) keeps the old behaviour for long jumps, and its tool text says to take a
  fresh look afterwards rather than assume where it stopped.
- **The tap right after blind typing is refused unless it came from a zoom.** On an app that withholds
  its tree, the reply box is a thin strip directly on top of the post below it, so a grid-cell tap
  aimed at it landed on that post and opened it — **twice out of two** on the same Moments reply box.
  After a `type_text` on such an app, only a tap carrying `on="zoom"` is accepted, with an error that
  says why; leaving the box clears the rule. Zoom-then-tap is how the same comment now sends on the
  first attempt.
- **`submit_input` no longer reports success on a box that cannot be submitted that way.** WeChat's
  comment box declares `IME_FLAG_NO_ENTER_ACTION` and sends only from its own button; firing the IME
  action there answered "done" while sending nothing. It now says it cannot, and names the app's own
  send button. `type_text` and `submit_input` also work when the tree has no focus node but our input
  connection is bound to the field.
- **The tap ring is drawn where the tap landed.** The marker window is positioned in display pixels, but
  an API 30+ overlay fits the system-bar insets by default, so its frame began below the status bar and
  **every ring sat that far under the real tap**. It now carries the same `FLAG_LAYOUT_IN_SCREEN` /
  `fitInsetsTypes = 0` / cutout mode the ball window already had. The caption's 0-1000 numbers were
  always right.

### Changed

- **The tool text now corrects three things models kept getting wrong.** `zoom_screen_region`'s
  `x/y/w/h` are **0-1000 of the whole screen, never pixels of an image** — a screenshot arrives
  downscaled (often ~576 px wide as the model sees it), and every zoom now reports the rectangle it
  actually showed, so a model can notice it was in the wrong space. `type_text`'s text states that a
  box which opened with the keyboard is **already focused** and should be typed into without a
  preliminary tap. And the screenshot text states that **the assistant's own ball is never in a
  capture** — the device blanks its overlays for the instant of capture — because a model that saw a
  round blue shape blamed it for covering a button and tried to route around it.
- **The README's first image is now a phone with the character sitting on it** rather than a floating
  head. `images/brand/andee-device.png` is the new hero art, and the generator places it 720 px wide,
  bottom-right, keeping 60 px of white padding with a 40 px analytic edge ramp; the mood strip narrows
  to 512/88 so the phone's left corner clears the last cell, and the text-to-art gap check now measures
  the character's left edge instead of a hard-coded offset. All four generated images were regenerated;
  **the round avatar is byte-identical**, because it still uses the head-only asset. The character in
  this render has a body — the app still draws a floating sphere.

## Download

Android 11+ (`minSdk 30`). The APK is **per-ABI** (`splits` in `app/build.gradle`), so pick the file
that matches your device:

| File | Take it if |
|---|---|
| `andee-0.5.2-debug-arm64-v8a.apk` | anything bought in the last several years — **this is the one for almost everyone** |
| `andee-0.5.2-debug-armeabi-v7a.apk` | an older 32-bit device |
| `andee-0.5.2-debug-x86_64.apk` | an emulator |

### This build is deliberately bare

It is built from source with nothing configured — **verified against the generated `BuildConfig`, not
assumed**:

- `CODEFLYING_ENABLED` is `false`, and both `CODEFLYING_KEY` and `CODEFLYING_DOMAIN` are empty, so
  **CodeFlying is not available in this build** and nothing is pre-wired to a hosted backend.
- **The Google voice settings are empty too**, so this build comes up on **Volcengine** and has no
  provider key of any kind baked in.
- `DEFAULT_LANG` is `en`: a device that has never picked a language comes up in **English**.
- The thinking default is off.

### The two keys you have to supply yourself

**The assistant cannot do anything until you give it two keys.** Open **⚙ → Backend → On-device** and
fill in:

1. **The model key (LLM)** — an OpenAI-compatible endpoint plus a model name. On an English UI these
   default to `https://api.openai.com/v1` and `gpt-4o-mini`; a Chinese UI defaults to
   `https://api.deepseek.com` and `deepseek-flash`.
2. **The voice key** — speech recognition and synthesis. Pick the provider first (**Voice provider** →
   Volcengine or Google), then fill in that provider's key: a Volcengine Speech key, or a Google Vertex
   Express key plus a GCP project *number* and a location. Optional: without it the assistant is silent
   but still works on screen.

Then, in this order: grant **Overlay** → enable **Accessibility** → tap the ball. Until the keys are
in, the card the assistant puts up will name what is missing — that is the self-check working, not a
fault.

> **Would you rather not configure keys at all?** Then this APK is the wrong door. Use the one-click
> page instead — **[codeflying.app/andee](https://www.codeflying.app/andee)**, or
> **[codeflying.net/andee](https://www.codeflying.net/andee)** in mainland China. Describe what you
> want, tap the build button, and you get a package with the **tokens already configured** plus a QR
> code to scan. Starting is free and the free token allowance is **finite — once it runs out, tokens
> must be bought.** It is a separate service with no direct relationship to this project, with its own
> terms, pricing and data handling.

### Why a debug build, when the README says not to hand one out

Because the alternative, today, is no binary at all. The README's advice still stands for anything you
*distribute*: a debug APK is `debuggable`, and its certificate is the **shared Android debug key** —
so it cannot install over a release-signed build, which means moving from this to a signed release
takes an uninstall, and an uninstall takes the notebook and the vault with it. Use this to try the
thing, not to hand it to someone who will depend on it.

## Known issues

- **The zoom-then-tap rule is deliberately blunt, and it expires rather than persisting.** After blind
  typing, *every* plain grid-cell tap is refused, including one aimed somewhere legitimate on the same
  screen — the model has to zoom first. That costs a turn on an app that hides its tree, and it is the
  trade taken: the alternative was landing on the post underneath, which cost several. The rule also
  lifts by itself after two minutes, and clears as soon as the box goes away, so a task that typed and
  moved on is not haunted by it.
- **`fling=true` still coasts unpredictably.** The option exists for long jumps, and its text says so,
  but nothing verifies where the list stopped — a model that flings and then assumes a position will
  still be wrong.
- **The wake threshold's margin is thin**, carried from `v0.3.2` and unchanged here: the eight measured
  judgements sit in 1.47–2.05 with the line landing in the gap between 1.69 and 1.77 — 0.08 wide. There
  is still no quality gate on enrolment takes.
- **A light generated page still fades in over a dark stage.** `TextPage`, `TracePage`,
  `Theme.Body.Fullscreen`'s window background and `HtmlActivity`'s WebView backdrop are all still dark.
  Carried over from `v0.3.1`; the app's own default has been light since `v0.4.1`.
- **A build with CodeFlying compiled in but no API key can still raise the wrong complaint.** The
  availability test looks at `CODEFLYING_ENABLED` and the domain rather than the key. Carried from
  `v0.1.1` onward; not fixed by this release.
- **`assets/andee_key.txt` is tracked by git and is not in `.gitignore`.** It ships empty, which is
  correct — the per-user token is written in at package time. But a local build that fills it in would
  be a key in a tracked file, and nothing currently stops that being committed.
- The two issues `v0.1.0` listed are **unchanged and untouched in this release**:
  `tools/verify_faces_lab.py` still reports 7/16 assertions passing against the committed
  `reports/ball-faces-lab.html`, and the debug WebSocket server (`net/BodyWsServer`) still binds
  `0.0.0.0:9008` with no authentication (documented in `SECURITY.md`).

## Before you install

Read **[DISCLAIMER.md](../../DISCLAIMER.md)** and
**[docs/acceptable-use.md](../acceptable-use.md)** first. This app asks for accessibility, overlay,
notification access, SMS and call log, and it can complete a payment by tapping. The only guardrail on
that path is Android's `FLAG_SECURE`; the prompt-level checks on risky actions are instructions to the
model, not enforcement.

## Install from source

If you would rather build it yourself — or need a *signed* release build, which is what you should
actually distribute:

```bash
git clone https://github.com/kuafuai/andee
cd andee
git checkout v0.5.2
./gradlew :app:assembleDebug      # installs as-is, signed with the debug certificate
```

To reproduce the attached build exactly, leave `local.properties` with no `CODEFLYING_*` keys, no
`GOOGLE_VOICE_*` keys, and `DEFAULT_LANG=en`; that is the whole configuration, and nothing is passed
on the command line.

`assembleRelease` needs your own keystore — the repo has none, so it produces an unsigned APK that
will not install until you sign it. Full from-scratch setup, including the JDK traps, is in the
README's **Provisioning** section.

**Upgrading from v0.5.1:** `versionCode` moves `10 → 11`, so this installs over it normally. Nothing
you configured is discarded. The two fixes change what the model does, not what the device stores, so
there is nothing to migrate — a device that has been running v0.5.1 behaves the same at rest and
differently the next time it swipes.
